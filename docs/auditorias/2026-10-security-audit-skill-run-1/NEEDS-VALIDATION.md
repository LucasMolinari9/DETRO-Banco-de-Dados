## NV-1. Deploy smoke runs the deployed commit's code with VERCEL_AUTOMATION_BYPASS_SECRET on any successful deployment_status, with no fork, creator or trusted-ref guard

- **fingerprint:** `deploy-smoke.yml:deployment-status:checkout-deployment-sha-with-bypass-secret`
- **verificação independente (Fase 5):** verified

### Descrição

The `smoke` job in .github/workflows/deploy-smoke.yml (at 539abe2) runs on every `deployment_status` event. Its `if:` only requires state == 'success' and a non-empty environment_url or target_url (lines 30-34). It has no creator, head-repository, fork or trusted-ref condition and no `environment:` approval gate. The secret-bearing jobs in db-checks.yml (line 79) and deriva.yml do have such a guard: they skip pull_request runs whose head repository is not this one.

VERCEL_AUTOMATION_BYPASS_SECRET is placed in job-level env (line 41), so every step sees it. actions/checkout (line 61) has no `ref:`, so it checks out the event's GITHUB_SHA, which for deployment_status is the commit being deployed. The last step (line 100) then runs `node scripts/check_deploy.mjs` from that checkout. The AUD-01 host allowlist that is supposed to confine the secret lives inside the same checked-out script. Its production hosts are read from the same checkout's app.js (check_deploy.mjs:35-41). It therefore constrains only an honest commit. Even the honest script sends the secret as `x-vercel-protection-bypass` (line 61) to the deployment under test, and a fork-built preview of this Vercel project matches PREVIEW_DO_PROJETO (line 34).

I re-read every cited line at 539abe2 and confirmed each one. vercel.json has no git/github integration settings that would disable deployments. The retained hunter artifact agents/h07-deploy-edge/artifacts/check-05.out shows three things: the rendered `if:` has no guard tokens, there is no environment, and a fixture check_deploy.mjs that differs from main receives the dummy secret through the job env. No further local reproduction was decisive: the source path is complete and unrefuted.

Whether a lower-trust actor can actually reach this job is unobserved, and so is what it would get. That depends on four things. First, whether the Vercel GitHub integration is connected; CLAUDE.md:272 only instructs connecting it. Second, whether Vercel deploys fork pull requests, automatically or after a team member authorizes them under Git Fork Protection. Third, whether GitHub then raises a success deployment_status in this repository for the fork's sha and runs this workflow with repository secrets, and whether that run uses the default-branch workflow file or the one in the deployment commit. If it uses the deployment commit's file, exposure extends to every repository secret. Fourth, whether the repository is public: ADR-0003 says so, but run metadata reports it private. These are Vercel and GitHub hosted facts. The changelog downgraded AUD-01 because the URL comes from Vercel or from repository writers (docs/CHANGELOG.md:21). That rationale does not address who authored the commit being deployed and executed.

### Causa raiz alegada

A privileged deployment_status job trusts both the code and the deployment of whatever commit the event names. Secret confinement (the host allowlist in scripts/check_deploy.mjs, fed by HOSTS_PROD from the same checkout's app.js) is implemented in the checked-out deployment-commit code instead of in trusted workflow configuration. The job has no condition excluding deployments of commits not authored on this repository's own branches: no fork, creator or trusted-ref guard and no environment gate. Its sibling secret-bearing PR jobs do exclude forks.

## NV-2. Owner-only `postgres` backup credential can reach code from any ref an agent or other writer pushes or dispatches (repository secret, no environment or ref binding)

- **fingerprint:** `github-workflows/backup-private.yml:SUPABASE_BACKUP_DATABASE_URL:repo-scoped-secret-unbound-to-ref`
- **verificação independente (Fase 5):** verified

### Descrição

docs/backup.md:50-57 tells the owner to add SUPABASE_BACKUP_DATABASE_URL as a repository secret and says only the owner adds it and that the URI must never be sent to the agent/chat. The same page then names the agent as the one who dispatches the backup workflow. scripts/backup_private.py:45 accepts only the user `postgres.gontnlfmothfglssbyyk`, which is the owner role of the sole shared database, not a minimal read-only login. backup-private.yml runs on workflow_dispatch (line 6). Job `backup` (line 16) has no `environment:` and no condition on github.ref, and it passes the secret (line 70) to `python3 scripts/backup_private.py` (line 73) checked out from the dispatched ref. Every guard in the script (pooler/verify-full URL validation, age recipient regex at :125, fixed error messages, upload of the .age file only) is therefore code the dispatcher chooses, not a boundary. GitHub's model gives anyone who can run their own code in a workflow effective read access to repository secrets. There are three ways to do that: (a) push a branch that changes only scripts/backup_private.py, then dispatch backup-private.yml on that branch (needs Actions write); (b) open a same-repo PR or push a branch that adds or edits a workflow file referencing `${{ secrets.SUPABASE_BACKUP_DATABASE_URL }}` (pull_request runs at db-checks.yml:66 and deriva.yml:47 use the PR's own workflow definitions, and the fork-exclusion `if:` at db-checks.yml:79 does not exclude same-repo branches); (c) push a branch whose new workflow triggers on push. Path (c) has a precedent: CHANGELOG:1366-1369 records that the agent session could not dispatch workflows at the time, so the owner had a temporary workflow triggered by a branch push. That precedent shows agent-pushed workflow code ran in Actions. It does not show a privileged secret was received: backup.yml uses no secrets, only the public anon key. Code reached this way can print the URI in transformed form to beat log masking, connect with owner rights, or write a plaintext or self-keyed dump to the upload path (line 78). Who can read run logs and artifacts depends on repository visibility, which is unobserved: ADR-0003 records 'public', while GitHub metadata reportedly says private. SUPABASE_TEST_AUDIT_DATABASE_URL is exposed to same-repo PR code the same way (db-checks.yml:79-83, deriva.yml:60-64). This contradicts the claim in the phase3-security.yml:9 header that 'o secret não é exposto a PRs', but that credential is minimal, so its impact is low. Whether the gap is exploitable depends on GitHub panel state: where the secret is scoped, and the push, workflows and dispatch permissions of the agent identity and of any other writers.

### Causa raiz alegada

Two secrets that carry authority above a branch writer are stored at repository scope. The workflows that consume them take their code from a ref the caller selects: workflow_dispatch on any branch, same-repo pull_request, or a push to any branch. No GitHub Environment with a main-only deployment-branch policy and an owner reviewer binds them to reviewed code. So the documented boundary, that the agent dispatches but never receives the URI (docs/backup.md:53,57), is enforced by nothing in source. Under GitHub's model, every principal that can push code and run a workflow can read every repository secret.

## NV-3. Anonymous Realtime subscriptions multiply owner bulk writes on the single shared Supabase project; only unobserved hosted quotas limit this

- **fingerprint:** `realtime:anon-postgres-changes:bulk-publication-subscription-amplification`
- **verificação independente (Fase 5):** replace

### Descrição

The anon JWT for project gontnlfmothfglssbyyk (role anon, exp 2036) is a literal in the public bundle and is used on every host. Anyone can therefore open Realtime WebSockets with it and join postgres_changes bindings on the 15 published tables. initRealtime shows the pattern: one public channel 'divat-rt' with 15 unfiltered event:'*' bindings, no private:true and no Realtime Authorization. Nothing in the repository limits how many connections, channels or duplicate bindings an anonymous client creates; opening many portal tabs already does this. RT_TABLES, which check_realtime.mjs requires to equal the live publication, includes the large tables itinerario_teste, qh_intervalo_teste and qh_predeterminado_teste. On 03/10/2026 one owner transaction inserted 52,385 + 9,553 + 25,748 = 87,686 rows into those tables. Routine loads are CSV imports through the Table Editor of 'what changed' (docs/etl.md:30-33), so their size and frequency are not evidenced. Supabase documents that postgres_changes checks each change against every matching subscription when RLS is enabled, as it is on every public table here. The number of authorization checks and delivered messages per owner write therefore grows linearly with the number of subscriptions an attacker holds. That work runs on the same database that serves every visitor's REST reads and counts against the project-wide Realtime connection and message allocation. The anon statement_timeout (an ALTER ROLE setting applied at login, not on SET ROLE) and pgrst.db_max_rows (PostgREST only) do not bound this path. eventsPerSecond:5 is only appended to the WebSocket URL by the client. Limits: the attacker cannot write data or choose when owner writes happen. Their cost is holding idle sockets with heartbeats. The portal falls back to REST without live updates if Realtime fails. This is exactly the comparable baseline (standard Supabase anon key + RLS + postgres_changes), which Supabase documents as scaling with subscriber count. That is calibration only. Whether hosted per-project quotas, internal poller timeouts or plan restrictions make the amplified cost material for this project cannot be observed from source.

### Causa raiz alegada

The portal exposes postgres_changes to the anonymous role on a publication that includes large, bulk-written tables. No repo-side control limits how many subscriptions there are: no private channel or realtime.messages authorization, no statement-level change signal replacing per-row changes, and no step that takes the large tables out of the publication during imports. check_realtime.mjs even requires them to stay published. The upstream per-subscription cost of each owner write therefore grows with the number of subscriptions an attacker chooses to hold. The only bounds are hosted per-project Realtime quotas and server internals that the repository neither sets nor records.
